# 보안 — 무엇을 잃을 수 있고 무엇은 못 잃는가

이 문서는 **키와 서명**에 관한 것입니다. 컨트랙트 보안이 아닙니다.
컨트랙트는 커스텀 코드가 0줄이라 감사 대상이 없고(D-001), **실제 리스크 표면은 개발자 노트북과 키 관리**입니다.

---

## 유출 시 손실 (D-019 적용 후)

| 유출된 것 | 손실 |
|---|---|
| Basescan API 키 | 0 — 서명 불가 |
| RPC 주소 | 0 — 서명 불가 |
| 주간 해시 지갑 키 | 가스비 잔액 + 가짜 해시 게시 위험 |
| **배포 지갑 키** (배포 완료 후) | **0** — 잔고를 비웠으므로 |
| **Safe 키 1개** | **0** |
| Safe 키 2개 | 타임락 물량 위험. 단 LP 인출은 **7일 예고** |
| 베스팅 물량 조기 인출 | **어떤 키로도 불가** |

**단일 키 유출로 잃는 것이 없는 구조입니다.** 이게 D-019의 목적입니다.

**다만 키 유출보다 흔한 손실이 하나 더 있습니다 — 주소를 잘못 보내는 것.** 아래를 보세요.

## 주소를 잘못 보내면 — 회수 가능성은 셋으로 갈립니다

**이것은 홀더가 실제로 겪을 수 있는 손실입니다.** 키 유출보다 훨씬 흔합니다.

| 잘못 보낸 곳 | 회수 | 방법 |
|---|---|---|
| **토큰 컨트랙트** | ❌ **영구 소실** | 없습니다 |
| **베스팅 둘** | ⚠️ 가능하되 **베스팅 일정을 탑니다** | `release()` → 타임락 |
| **운영 타임락** | ✅ 가능 | Safe 예약 → 7일 → 실행 |

주소는 [`WALLETS.md`](WALLETS.md)에 있습니다.

### 토큰 컨트랙트로 보낸 것은 아무도 못 꺼냅니다

`src/Token.sol`에는 `rescue`도 `recover`도 `owner`도 없습니다. 토큰을 꺼내려면 그 컨트랙트가
`transfer`를 호출해야 하는데, **컨트랙트는 스스로 움직이지 못하고 깨워줄 함수도 없습니다.**

**이것은 버그가 아니라 D-001의 대가입니다.** 구조 함수를 넣으면 「발행자가 컨트랙트에서
토큰을 꺼낼 수 있는 권한」이 생깁니다. 그 권한은 감사 대상이 되고, 무엇보다
**"발행자만 쓸 수 있는 출구"가 하나 생깁니다.** 꺼낼 수 없다는 것과 아무도 못 꺼낸다는 것을
맞바꿨습니다.

> **이건 약속이 아니라 사실입니다.** 「회수해드리겠습니다」라고 쓸 수 없는 이유는
> 제가 인색해서가 아니라 **코드에 그럴 방법이 존재하지 않기 때문**입니다. (D-014)

거래소 주소 대신 토큰 컨트랙트 주소를 복사해 보내는 사고는 흔합니다.
대부분의 표준 ERC-20이 같은 성질을 갖습니다.

### 베스팅으로 보낸 것은 늦게, 그리고 타임락으로 갑니다

`VestingWallet`은 **현재 잔고 전체**를 기준으로 해제량을 계산합니다.

```solidity
function vestedAmount(address token, uint64 timestamp) ... {
    return _vestingSchedule(IERC20(token).balanceOf(address(this)) + released(token), timestamp);
}
```

그래서 나중에 들어온 토큰도 그 일정을 그대로 탑니다. USDC 같은 다른 토큰을 보내도
`release(그 토큰)`으로 꺼낼 수 있지만 **똑같이 최대 4년에 걸쳐** 나옵니다.

**그리고 도착지는 언제나 `owner()` = 타임락입니다.** 보낸 사람에게 자동으로 돌아가지 않습니다.
돌려주려면 그 뒤에 제가 따로 보내야 하고, 그건 코드가 아니라 제 행동입니다.

### 역설적으로 타임락이 가장 안전합니다

`execute()`가 임의 호출을 실행할 수 있어서, Safe에서 예약하고 7일 뒤 회수할 수 있습니다.

## 저장소와 의존성이 바뀌지 않았는지

**공급망 공격은 「남이 준 코드를 실행하는 것」과 다릅니다.** 내가 이미 쓰기로 한
라이브러리가 조용히 바뀌거나, 저장소의 코드가 한 줄 수정되는 쪽입니다.
알아채기 어렵고, 실제 사례가 여럿 있습니다.

**아래 세 줄이면 확인됩니다.** 배포 전과 의존성을 건드린 뒤에 돌리세요.

```bash
# 1. lib/ 이 수정됐는가 — 앞에 + 가 붙으면 누가 파일을 고친 것입니다
git submodule status

# 2. 고정된 커밋이 공식 태그와 같은가
git ls-remote https://github.com/OpenZeppelin/openzeppelin-contracts refs/tags/v5.4.0^{}
git ls-remote https://github.com/foundry-rs/forge-std refs/tags/v1.16.2^{}

# 3. 코드가 여전히 통과하는가
forge build && forge test
```

**기준값** — `foundry.lock`에 박혀 있습니다.

| 라이브러리 | 태그 | 커밋 |
|---|---|---|
| `openzeppelin-contracts` | v5.4.0 | `c64a1edb67b6e3f4a15cca8909c9482ad33a02b0` |
| `forge-std` | v1.16.2 | `bf647bd6046f2f7da30d0c2bf435e5c76a780c1b` |

**2026-08-23 확인 — 둘 다 공식 태그와 일치했습니다.**

### 무엇이 잡히고 무엇이 안 잡히는가

| 공격 | 잡히나 |
|---|---|
| `lib/` 파일을 몰래 수정 | ✅ `git submodule status`에 `+` |
| 서브모듈을 다른 커밋으로 교체 | ✅ 해시가 `foundry.lock`과 불일치 |
| OpenZeppelin 저장소 자체가 털림 | ✅ 공식 태그 해시와 대조 |
| 배포된 바이트코드 ≠ 저장소 소스 | ✅ **Basescan 소스 검증** |
| AI가 코드를 몰래 고침 | ✅ `git diff` + 테스트 |
| **내 PC가 이미 감염됨** | ❌ — 위 검사도 감염된 PC에서 돕니다 |

**가장 강한 방어는 이미 걸려 있습니다.** 네 컨트랙트가 Basescan에 검증돼 있어
**배포된 바이트코드가 공개된 소스와 같다는 것이 증명**됩니다. 무엇이 심어졌든 그 시점에 드러납니다.

마지막 줄은 정직하게 남겨둡니다. **PC가 감염되면 모든 자체 검사가 무의미합니다.**
그래서 「남이 준 코드는 실행하지 않는다」가 아래 절에 따로 있습니다.

### 버전을 올릴 때

**OpenZeppelin 버전을 함부로 올리지 마세요.** `VestingWallet`의 해제 계산이나
`TimelockController`의 역할 구조가 바뀌면 공지한 일정이 조용히 달라집니다.

올릴 일이 생기면 — ① 위 세 줄로 새 커밋 해시를 확인하고 ② 63개 테스트를 돌리고
③ `docs/DECISIONS.md`에 왜 올렸는지 남깁니다.

## 계정 2단계 인증 — 지갑 밖에도 잃을 것이 있습니다

이 문서의 나머지는 키와 코드 얘기지만, **계정도 자산입니다.**
`Yumi-Token` 깃허브 계정이 탈취되면 **사칭 주소를 공식 저장소에 올릴 수 있습니다.**
「공식 주소는 저장소 한 곳에만」이라는 방어선이 통째로 무너집니다.
디스코드도 마찬가지로, 발행자 계정이 곧 신원입니다.

### 순서

**계정 2FA 를 먼저 켜고, 그 다음에 서버 요구를 켭니다.**

🔴 **순서를 바꾸면 `scripts/discord_setup.py` 가 깨집니다.**
서버에 2FA 를 요구하면 **봇의 관리 작업도 봇 소유자 계정의 2FA 를 확인**합니다.
계정에 2FA 가 없는 채로 서버 요구만 켜면 봇이 채널·역할을 만들지 못합니다.

### 디스코드

| | |
|---|---|
| 계정 | 사용자 설정 → 「내 계정」 → 2단계 인증 활성화 |
| 서버 | 서버 설정 → 안전 설정 → 「관리자 작업에 2단계 인증 요구」 (소유자에게만 보임) |

### 깃허브

Settings → Password and authentication → Two-factor authentication

### ⚠️ SMS 인증은 켜지 않습니다

**SIM 스와핑** — 통신사를 속여 번호를 자기 유심으로 옮기는 수법이고,
크립토 계정이 1순위 표적입니다. SMS 백업을 켜두면 2FA 강도가 SMS 수준으로 떨어집니다.
**인증 앱만 씁니다.** 가능하면 보안 키(패스키)를 함께 등록하세요 —
6자리 코드는 가짜 로그인 페이지에 속아서 입력할 수 있지만 보안 키는 도메인을 확인합니다.

### 🔴 백업 코드를 저장소에 넣지 마세요

폰을 잃으면 백업 코드가 계정을 되찾는 유일한 방법이고,
디스코드·깃허브 모두 2FA 분실 복구를 거의 해주지 않습니다.

| 저장할 곳 | 저장하면 안 되는 곳 |
|---|---|
| 비밀번호 관리자 · 인쇄물 · 오프라인 USB | **이 저장소 안 어디든** · `.env` · 이메일 · 평문 클라우드 메모 |

**저장소는 나중에 Public 이 됩니다.** 시드 문구와 같은 등급으로 다루세요.

## 유출을 알았을 때 — 순서가 중요합니다

```
1. 남은 키 2개로 Safe 명부에서 유출된 키 제거 + 새 키 추가   ← 제일 먼저
2. 배포 지갑에 잔고가 있으면 Safe로 이동
3. 예약된 트랜잭션 확인 → 내가 안 한 게 있으면 즉시 취소
4. 기록에 그대로 공개
```

**3번을 먼저 하면 안 됩니다.** 공격자가 재예약하며 시간을 끄는 동안 명부를 못 고칩니다.
명부 변경은 타임락을 거치지 않으므로 **먼저 하는 쪽이 이깁니다.**

## 서명 — 다운로드를 안 해도 자산은 나갑니다

| 위험한 서명 | 뜻 |
|---|---|
| `approve` 무제한 | 이 주소가 내 토큰을 **한도 없이** 가져감 |
| `setApprovalForAll` | NFT 전부 |
| `permit` | 가스도 안 드는 오프체인 서명인데 **토큰 이동 권한이 넘어감** |

**하드웨어 지갑은 키를 지키지 서명을 지키지 않습니다.** 악성 승인을 누르면 기기는 충실히 서명합니다. 특히 **블라인드 서명**(기기 화면에 해시만 뜨는 경우)을 그냥 넘기면 하드웨어를 쓰는 의미가 사라집니다.

**규칙 셋**

- **자주 쓰는 사이트는 북마크로만.** 검색 결과 클릭 금지 — 광고에 가짜가 섞입니다
- **승인 창이 뜨면 상대 주소와 한도를 확인.** 무제한 승인 금지
- **2FA는 문자 말고 앱이나 보안키로**

## 남이 준 코드는 실행하지 않습니다

2026년 상반기 북한 연계 공격이 **한국 19건 / 미국 8건**으로 한국이 1순위이고, 표적이 거래소가 아니라 **개인 개발자**로 옮겨갔습니다. 한 캠페인만으로 감염 시스템 2,726대에서 지갑 26,584개가 털렸습니다.

**주 경로: 가짜 채용 → 코딩 테스트 → 실행하는 순간 감염.** 프로젝트가 정상 작동해서 의심할 이유가 없고, 악성코드가 실행 파일이 아니라 **이미지 파일 주석에 Base64로** 숨겨져 있던 사례도 있습니다.

| | 기준 |
|---|---|
| **내가 고른 도구** | Foundry, OpenZeppelin — 검증된 것, 버전 고정 |
| **남이 보낸 코드** | **절대 안 돌림. 예외 없음** |

`npm run dev` / `npm start`를 하라고 하면 **그 시점에 의심하세요.** 꼭 봐야 하면 지갑이 없는 격리된 가상머신에서만.

**이 프로젝트는 공개 활동이 목적이라 접근이 반드시 옵니다.** "협업하고 싶다", "감사해드리겠다", "투자 검토 중이다" — 전부 옵니다.

## 이 문서가 다루지 않는 것

컨트랙트 취약점. 커스텀 코드가 0줄이라 다룰 대상이 없습니다.
기능을 하나라도 추가하는 순간 이 문장이 거짓이 되고, 그때는 감사가 필요합니다. (D-001)
